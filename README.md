# Ratatosk для компьютера

[![проверки](https://github.com/sharap/Ratatosk-desktop/actions/workflows/ci.yml/badge.svg)](https://github.com/sharap/Ratatosk-desktop/actions/workflows/ci.yml)

Клиент мессенджера Ratatosk: Kotlin и Compose Multiplatform поверх ядра
[`ratatosk-core`](https://github.com/sharap/ratatosk-core), написанного
на Rust.

Переписка шифруется, адресов на сервере нет, и сообщение идёт тем путём,
какой доступен прямо сейчас: по локальной сети, через Tor, через почту
или через меш Yggdrasil. Ступень выбирает ядро и честно говорит клиенту,
куда уйдёт следующее сообщение, — окно только показывает это словами
ядра, а не придумывает свои.

Рядом живёт [клиент для Android](https://github.com/sharap/Ratatosk-android);
это его настольный брат, а не обёртка вокруг него.

## Что умеет

* личные чаты, группы и каналы: подписка по ссылке, приём по приглашению,
  права на запись и впуск, раздача архива, листание истории назад;
* вложения с превью, реакции, ответы, правки, поиск по переписке;
* голосовые сообщения — запись и прослушивание с перемоткой;
* видеосообщения-кружки — **только просмотр**: записывать их на
  компьютере пока нечем;
* уведомления по чатам с выбором «молчать» и «молчать до такого-то часа»;
  выбор держит ядро, и он никуда не едет — это дело этого устройства;
* два режима: полный клиент, где ключи лежат здесь, и сопряжённое
  устройство, где ключи остаются на телефоне, а компьютер работает
  вторым экраном (ссылка `ratatosk:v0:pair:…`);
* ступени связи: локальная сеть, Tor, почта, меш Yggdrasil, рандеву
  через реле nostr, а на Linux — ещё и эфир Bluetooth: он находит людей
  рядом вообще без сети;
* ссылки `ratatosk:v0:…` и показ QR; отпечаток сверяется голосом,
  и до сверки контакт показывается непроверенным.

Чего пока нет: чтения QR с экрана или из файла и записи кружков.

## Состояние

Ранняя версия, 0.1.0 — как и у Android-клиента. Снаружи приложение
никто не проверял, и готовых сборок мы пока не выкладываем: собирается
из исходников, как описано ниже.

## Сборка

Нужны:

* JDK 17. Им же собирается пакет: `jpackage` берётся из того же JDK, а в
  JBR из Android Studio (частый `JAVA_HOME`) его нет;
* Rust с `cargo` — ядро собирается из исходников каждой сборкой;
* на Linux — `libdbus-1-dev` и `pkg-config`: сборка ядра сама включает
  эфир (`bt` поверх BlueZ), и без заголовков dbus она останавливается
  на середине, когда всё остальное уже собралось
  (`sudo apt install libdbus-1-dev pkg-config`);
* исходники [ядра](https://github.com/sharap/ratatosk-core) рядом с этим
  репозиторием (или свой путь через `-Pratatosk.core.dir=…`);
* `ffmpeg` в системе — им играются и записываются голосовые и
  проигрываются кружки. Без него всё остальное работает, а запись и
  просмотр честно говорят, что играть нечем. Собранный `.deb` объявляет
  эту зависимость сам, так что при установке пакетом `ffmpeg` приедет
  вместе с ним;
* Gradle подтягивается обёрткой (`./gradlew`), ставить не нужно.

```sh
git clone https://github.com/sharap/ratatosk-core
git clone https://github.com/sharap/Ratatosk-desktop
```

```
.
├── Ratatosk-desktop/   <- этот репозиторий
└── ratatosk-core/      <- ядро
```

Дальше обычное:

```sh
./gradlew :app:run                          # запустить
./gradlew :app:test                         # проверки
./gradlew :app:packageDeb                   # .deb для Debian и Ubuntu
./gradlew :app:packageUberJarForCurrentOS   # один jar под системную JVM
```

Пакет собирается переносимым между Debian и Ubuntu, и это не бесплатно:
зависимости ему выписывает `jpackage` по библиотекам **машины сборки**,
а в Ubuntu 24.04 половина из них переименована переходом на 64-битный
`time_t` (`libasound2` → `libasound2t64`). Поэтому после сборки
`tools/portable-deb.sh` дописывает в пакет список через `|` — из пары
имён на системе есть одно, и его достаточно. Тем же скриптом можно
починить чужой пакет, собранный без него:

```sh
tools/portable-deb.sh ~/Загрузки   # каталог, где лежит .deb
```

Библиотеку ядра и привязки к ней собирает задача `buildRustCore`: они
кладутся в `build/generated/uniffi` и подключаются к сборке оттуда.
В репозитории их нет и быть не должно — это артефакт ядра, а не исходный
код этого проекта. Признаки ядра перечислены в `gradle.properties`
(`ratatosk.features`).

Если ядро обновилось, а Gradle взял привязки из кэша:

```sh
./gradlew :app:test --rerun-tasks
```

### Другие машины

`.deb` собирается под ту архитектуру, на которой идёт сборка: `jpackage`
кладёт в пакет ту JVM, под которой работает. А вот один jar можно собрать
сразу с двумя библиотеками ядра:

```sh
./gradlew :app:packageUberJarForCurrentOS -Pratatosk.arm64=true   # + Linux arm64
./gradlew :app:packageDeb -Pratatosk.windows=true                 # + Windows x86_64
```

Для первого нужны линкер `aarch64-linux-gnu-gcc` и цель Rust
`aarch64-unknown-linux-gnu`, для второго — mingw. Сборка сама скажет,
чего не хватает, и назовёт команду.

## Устройство

```
app/src/main/kotlin/chat/ratatosk/desktop/
├── Main.kt        точка входа, окно, приём ссылок ratatosk:
├── core/          мост к ядру: запуск, журнал, реестр аккаунтов
├── backend/       шов: Backend (полный клиент и второй экран) и AppEvent
├── model/         модели по назначению поверх FeatureModel
├── ui/            экраны на Compose и Strings.kt
├── data/          настройки и секрет устройства (ключница системы)
└── util/          вспомогательное: ffmpeg, превью, ссылки, разметка
```

Два правила, которые видно в коде и стоит знать до правок:

* **окно не разговаривает за протокол.** Слова о каналах, об ожидании,
  об отказах и о ценах приходят из ядра (`channel_signal_text`,
  `channel_waiting_text`, тексты §15). Своя формулировка разошлась бы
  с поведением на первой же правке, а человек читал бы неправду;
* **команды идут через `Backend`, а не в ядро напрямую.** Во втором
  режиме клиента нет вовсе, и команда, ушедшая мимо шва, не «не
  сработает», а бросит исключение, которое проглотит `catch`: снаружи
  это выглядит как «кнопка не работает», без единого слова о причине.

## Проверки

```sh
./gradlew :app:test
```

Запущенное ядро им не нужно: модели проверяются поверх подставного
`Backend`. Собрать его всё же придётся — привязки к нему и есть часть
исходников сборки.

То же самое гоняется на каждый push и на каждый pull request
([`.github/workflows/ci.yml`](.github/workflows/ci.yml)), вместе со
сборкой `.deb`: тесты не трогают ни `jpackage`, ни ресурсы, и
«собирается» ломается отдельно от «работает». Метка `v*` запускает
[выпуск](.github/workflows/release.yml) — пакет и jar складываются
в черновик, публикует его человек.

Кроме поведения проверяется устройство — что каждая модель забывает своё
при выходе из аккаунта и что ошибка у окна и у моделей одна; обе эти
поломки уже случались, тихо и без исключений. Отдельная проверка сверяет
собранную библиотеку ядра с привязками: разошедшись, они дают падение на
первом же новом событии, а не внятную ошибку.
